Self-hosting is the trust anchor

The whole application is on GitHub under the MIT licence. The hosted version is a convenience, not a lock-in: run Bussola on your own box and you lose nothing — not a connector, not a widget, not a feature.

View the repository Quick start

Why self-host

Local-first

With no DATABASE_URL, Bussola runs on PGlite — Postgres compiled to WASM, stored in ./data/pgdata. No server, no Docker, nothing to install.

Encrypted secrets

API keys are sealed with AES-256-GCM at rest. Identity is Better Auth: email and password, sessions in your own database, no third-party identity provider.

One schema, one path

Postgres, and only Postgres — the same schema and the same queries on a laptop as in production. Moving from PGlite to a real server is one environment variable.

Quick start

Running in three commands

Node, then three steps. The database migrates itself on first start, so there is nothing to run first.

Terminal
# install & configure
npm install
cp .env.example .env.local

# optional but recommended — set it as BUSSOLA_ENCRYPTION_KEY
openssl rand -hex 32

# run it
npm run dev

Open localhost:3000 and claim the instance with an account only you hold. Self-hosted accepts exactly one account: the first person to reach /signup takes it, and every later attempt is refused.

Connections

Paste API tokens for Railway, Vercel, Netlify, Supabase, Sentry, Stripe, Lemon Squeezy, Resend and Qonto. Each is tested against the provider before it is saved.

Dashboards

Create a canvas. Widgets render labelled sample data until a source syncs, so you can lay the whole thing out before pasting a single token.

Edit

Drag, resize and add trackers, KPI blocks and charts. The layout saves itself as you go.

Deployment

From a laptop to a shared instance

The same build runs both ways. Set DATABASE_URL the moment more than one person depends on the install — PGlite serves exactly one process by design.

This is not two builds. Every query against tenant-owned data goes through the same organization-scoped repositories in both editions — so the self-hosted path exercises the very isolation code that keeps hosted customers apart, and the linter refuses to compile a route handler that reaches around it.

Architecture

Why a worker instead of fetch-on-render

Widgets never trigger a provider call. A background worker refreshes each connection on its own schedule and writes a snapshot; every widget request is then a single local query.

Traffic that scales with connections

Upstream calls track how many connections exist, not how many people are looking. That is what keeps a shared deployment from being rate-limited — or banned — by Railway, Supabase and especially Qonto.

Failure that gets quieter

A failing connection backs off exponentially to at most hourly, and after ten consecutive failures it stops syncing and the widget asks its owner to reconnect. Pasting new credentials clears the count and resumes immediately.

Workers that can be many

Workers claim connections with FOR UPDATE SKIP LOCKED and a lease, so several run at once without fetching the same connection twice — and one that dies mid-fetch just leaves its work to become due again.

History at a resolution you would plot

One sample per connection per hour, alongside the latest snapshot. A 60-second interval would write tens of thousands of rows per connection per month at a resolution nobody looks at.

MCP server

Give an agent a safe seat

Bussola ships an MCP server so an assistant can work with your data and your dashboards — inside limits that live in the server, not in a prompt.

Can do

  • Read data from every connector
  • Create and delete dashboards
  • Add, remove and move widgets
  • Enable or disable a connection

Cannot do

  • Edit connection credentials — web UI only
  • Write to a third-party system: restart a service, issue a refund, move money
  • Bypass plan limits or authentication
  • Reach another organization's data

Write actions on third-party systems are deliberately out of scope: doing that safely needs its own confirmation and audit design, and shipping it early would undo the read-only guarantee that makes handing over a token reasonable in the first place.

Contributing

A connector is a small pull request

Describe it

Add an entry to the provider catalog: name, tagline, which credential fields the form should ask for, and where to get the token.

Fetch it

Write one module that turns credentials into a typed snapshot. Connector modules stay purely about fetching — no UI, no storage.

Render it

Register the widgets: a name, a description, a default size. The catalog, the picker and the connections page pick it up from there.

Star it, fork it, ship a connector

Issues and pull requests are the point. If Bussola is missing the one source you check every morning, that is a small, well-scoped patch.
