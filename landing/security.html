Security

You are handing over tokens. Here is what happens to them.

Bussola only works if you give it read access to the systems that run your business. That is a real ask, so this page is specific about how those credentials are stored, what the application does with them, and what it is structurally unable to do.

Security at a glance

AES-256-GCM at rest

Every credential is encrypted before it reaches storage, and decrypted only in the process that makes the request.

Read-only connectors

No connector has a write path. Bussola cannot restart a service, refund a charge or move money — there is no code that could.

Isolation by construction

Every query against tenant data goes through organization-scoped repositories, in both editions — enforced by the linter, not by convention.

Your database

Self-hosted keeps everything on your own Postgres. Nothing about the product depends on our servers existing.

How credentials are handled

Credentials are entered in the web UI, encrypted with AES-256-GCM, and written to the database in that form. They are never logged, never included in error reports, and never returned to the browser after they are saved — a connection you edit shows a masked placeholder, not the stored value.

  • Per user, per organization. A credential belongs to the connection that owns it. Nothing is shared across tenants.
  • Web UI only. Credentials cannot be created or changed through the MCP server, and there is no API surface that returns them.
  • Verified on save. Adding a connection makes a live request to the provider first, so an over-scoped or invalid key is caught immediately.
  • Removed on delete. Deleting a connection deletes its stored secret along with the snapshots taken through it.
Use the narrowest token the provider offers. Stripe restricted keys with read access to Charges, Subscriptions and Balance are enough. Sentry needs only org:read and project:read. Supabase wants a personal access token, never a service key. Every connector page names the minimum.

What Bussola can and cannot do

The read-only boundary is not a policy, it is the shape of the code: connector modules expose fetch functions and nothing else. There is no method that issues a write to a provider, so no bug, prompt or misconfiguration can trigger one.

SurfaceCanCannot
ConnectorsRead deploys, errors, revenue, balancesWrite anything to a provider
MCP serverRead connector data, manage dashboards and widgetsRead or edit credentials, bypass limits or auth
Share linksRender one dashboard, read-onlyReveal credentials, or reach other dashboards
Sync workerFetch on a schedule, write snapshotsAct outside the organization that owns the connection

Authentication and sessions

Identity runs on Better Auth, inside the application and on the same Postgres as everything else. There is no external identity provider in the path, which means the hosted and self-hosted editions run the same auth code rather than two implementations.

  • Email and password, with sessions stored in your own database
  • HTTP-only, CSRF-checked session cookies
  • Self-hosted accepts exactly one account — the first signup claims the instance, later attempts are refused
  • Hosted gives every account its own organization at creation time

What data is stored

Connection snapshots
The latest response shape per connection — deploy states, balances, aggregate counts. This is what widgets read.
Hourly history samples
One sample per connection per hour, pruned against your plan's retention. Self-hosted keeps everything.
Account and organization records
Email, hashed password, session rows, organization membership, and — on the hosted edition — the Stripe customer and subscription ids.
Dashboards and layouts
Which widgets you placed, where, and on which canvas.

Bussola stores aggregates and status, not exports of your systems. The one place raw records are read through on demand is the Qonto transaction list, which is cursor-paginated and user-driven, behind a short per-tenant cache.

Hosted, and the alternative

The hosted edition runs on managed Postgres in the EU, with encryption keys held outside the database. If that is not a trade you want to make, the same application is MIT-licensed: run it on your own infrastructure and no third party — including us — is in the path at all.

Reporting a vulnerability

If you find a security issue, please report it privately first and give us a chance to ship a fix before it is public. Send the details — steps to reproduce, affected version, impact — to security@usebussola.com, or open a private security advisory on the repository.

  • We aim to acknowledge a report within three working days
  • We will tell you when a fix ships, and credit you unless you would rather we did not
  • Please do not run automated scanning against the hosted service, or test against data that is not yours

What this page does not claim

Bussola is a young product from a small company. It has no SOC 2 report, no ISO 27001 certificate and no third-party penetration test to point at yet — and saying otherwise would be the least trustworthy thing on a security page. What it does have is a public codebase you can read, a read-only design you can verify, and a self-hosted edition that removes us from the equation entirely.
